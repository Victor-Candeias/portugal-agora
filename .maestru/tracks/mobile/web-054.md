# WEB-054: Energia: workflow GitHub Actions de atualização dos dados de energia

## Contexto

O relatório `Documents/relatorio_energia_portugal.md` (secção 10) propõe um workflow com cron horário que faz commit dos dados em `public/data/energy/`. Hoje o `deploy.yml` só corre por `workflow_dispatch` e gera os dados estáticos no próprio build do Pages. O relatório refere como alternativa mais robusta gerar e publicar os dados no workflow do Pages.

## Objetivo

- **Opção (b), decidida pelo utilizador a 2026-10-19:**
  - os dados são gerados no `deploy.yml` do Pages, que passa a ter `schedule:` diário além do `workflow_dispatch`;
  - sem commits automáticos e sem `contents: write`, como no Carris e no Metro do Porto;
  - os dados de energia só existem no artefacto publicado, não no git.
- Agendamento: um deploy por dia, que também faz a reconciliação dos dados revistos. A recolha horária fica para quando houver intradiário (WEB-057). O cron do GitHub Actions não garante hora exata.
- Secret `ENTSOE_TOKEN` só no GitHub Actions: nunca no Vite, no bundle, nos JSON públicos nem nos logs.
- Se a recolha falhar, o script descarrega e republica os ficheiros já publicados no Pages (último dataset válido), sem bloquear o deploy do resto do site.
- O histórico de 30 dias é reconstruído em cada execução: pedir os 30 dias à REN ou juntar o `energy.sqlite` publicado com os dias novos. Decidir na spec.
- Cache do Pages: as apps leem os ficheiros com `no-cache`/ETag.

## Notas

- A opção (a), um workflow dedicado com commit diário dos dados, foi rejeitada: o repositório crescia com binários, exigia `pull` frequente, permissão de escrita e o encadeamento do deploy.
- O deploy diário publica também o resto do site e reconstrói os `.sqlite` do Carris, Metro e Serviços Públicos.
- No âmbito inicial (só diário, decisão de 2026-10-19) basta a reconciliação diária; a recolha horária fica para o WEB-057.

## Bloqueia

WEB-057, WEB-060.

## Resultado

- O `deploy.yml` passa a ter `schedule:` diário (`0 13 * * *` UTC, depois da publicação do dia anterior pela REN) além do `workflow_dispatch`. Ganha também `concurrency: pages`, para o deploy agendado e o manual não se sobreporem.
- Sem commits automáticos e sem `contents: write`.
- Node 22 com `check-latest: true`, para garantir a versão 22.18 ou superior (type stripping no `build-energy-db.mjs`).
- O passo `build:db` foi renomeado para «Build static data (Carris, Metro do Porto, Serviços Públicos, Energia)». A energia nunca o faz falhar: se a REN falhar, republica o dataset publicado (WEB-053).
- **Histórico de 30 dias:** é pedido de novo à REN em cada execução. São 32 pedidos de cerca de 1,4 KB, menos de 2 s. Isto reconcilia automaticamente os dados revistos e evita depender do `energy.sqlite` publicado. Não foi preciso spec, porque a alteração é num só ficheiro.
- O `ENTSOE_TOKEN` fica para o WEB-051/WEB-057, que ainda não usam o workflow.
- **Notas:**
  - O GitHub desativa os workflows agendados ao fim de 60 dias sem atividade no repositório.
  - Nada foi executado nem publicado neste PC: o agendamento só tem efeito depois de um `push` para o GitHub, que é decisão do utilizador.
