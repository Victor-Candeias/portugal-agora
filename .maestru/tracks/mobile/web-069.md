# WEB-069: Tráfego aéreo (core): cliente, normalização ADS-B, regiões, deduplicação e testes

## Contexto

Origem: `Documents/implementacao_trafego_aereo_web_mobile.md` (§2.3, §4, §5.4). Segue o padrão do core: um cliente e funções puras partilhados pela web, pelo mobile e pelo proxy (ex.: `packages/core/src/api/snsUrgencias.ts`). Depende das decisões do WEB-068.

## Objetivo

1. Em `packages/core/src/api/airTraffic.ts`, criar:
   - os tipos `Aircraft` e `AircraftSnapshot`, conforme o contrato §4.1;
   - o tipo `AirTrafficRegion` (`mainland` | `azores` | `madeira`), com o catálogo de centros e raios.
2. Criar o adaptador `normalizeAdsbLol(raw)`. Converte unidades:
   - pés para metros;
   - nós para km/h;
   - ft/min para m/s;
   - `seen` para `lastSeenUtc`.

   Também:
   - trata `alt_baro: "ground"` como `onGround: true`;
   - faz `trim` do `flight`;
   - rejeita coordenadas inválidas;
   - devolve campos ausentes como `null`, nunca como 0.
3. Criar `mergeSnapshots`, que deduplica por `icao24` entre centros e fica com o registo mais recente. Criar também `isSnapshotStale(generatedAt, staleAfter)`.
4. Criar o cliente `createAirTrafficClient({ baseUrl })`, que consome o proxy (WEB-070): `getAircraft(region)`, `getAircraftById(icao24)` e `getStats(region)`.
5. Criar as funções de formatação partilhadas: unidades (km/h ou nós, m ou pés), idade do sinal e «N/D».
6. Criar as constantes de avisos e atribuição: dados incompletos ou atrasados; não usar para navegação aeronáutica; o `callsign` não é um número de voo comercial.

## Critérios de aceitação

- Testes em `packages/core/test` para:
  - conversão de unidades;
  - timestamps;
  - o valor `"ground"`;
  - coordenadas inválidas;
  - campos ausentes devolvidos como `null`;
  - deduplicação entre centros;
  - `isStale`.
- Os tipos são usados pela web, pelo mobile e pelo proxy sem duplicação.
- Antes de implementar, criar uma spec (`implementation-plan-v1`).
