# WEB-053: Energia: pipeline diário REN → energy.sqlite + JSON (MVP)

## Contexto

O relatório `Documents/relatorio_energia_portugal.md` propõe uma pipeline sem backend: **fonte → GitHub Actions → SQLite/JSON → GitHub Pages**. O projeto já faz isto para o Carris, o Metro do Porto e os Serviços Públicos (`apps/web/scripts/build-*.mjs`, `pnpm --filter web build:db`). O mobile descarrega os `.sqlite` publicados (MOB-003).

Esta é a Fase 1 (MVP diário) do relatório, só com dados diários REN validados no WEB-050.

## Objetivo

- `apps/web/scripts/build-energy-db.mjs` (Node, como os outros scripts do repo, em vez do Python do relatório; confirmado pelo utilizador a 2026-10-19): fetch REN → parse → normalização (UTC, taxonomia do WEB-052) → validação → agregação → exportação.
- `energy.sqlite` com `energy_observation` e `energy_balance` (esquema da secção 7) e a tabela `meta` (`generated_at`), como os outros `.sqlite`.
- JSON leves em `public/data/energy/`:
  - `daily.json`: últimos 30 dias (produção renovável e não renovável em GWh, consumo, quota renovável ponderada);
  - `latest.json`: último dia disponível, com `freshness: "latest_available"` (nunca «agora»).
- Integrar no `build:db`.
- Não somar fontes: uma fonte canónica por métrica e intervalo, com proveniência.
- Se a fonte falhar, não publicar um dataset vazio ou parcial: manter o último dataset válido (descarregar e republicar os ficheiros já publicados no Pages, opção (b) do WEB-054).
- Uma falha nos dados de energia não pode partir o `build:db` das outras secções.
- Atualizar o README com as fontes de dados da energia (REN): licença, frequência e limitações.

## Validação

Casos da secção 13: erro HTTP, HTML ou JSON inesperado, timeout, duplicados, valores negativos, séries incompletas e tamanho dos JSON.

## Notas

- Spec obrigatória (`implementation-plan-v1`).
- Decidir na spec se as apps leem JSON, SQLite ou ambos.

## Bloqueia

WEB-054, WEB-055.

## Resultado

- `apps/web/scripts/build-energy-db.mjs` corre no fim do `build:db` e gera `public/data/energy/daily.json` (30 dias, cerca de 15 KB), `public/data/energy/latest.json` e `public/data/energy.sqlite` (com `energy_observation`, `energy_balance` e `meta`).
- **As apps leem só os JSON.** O SQLite fica publicado como arquivo (ver `web-053-spec`).
- Com dados reais, o último dia (2026-10-18) dá 99 GWh renovável, 16 GWh não renovável e 15 GWh de armazenamento, ou seja 76,15% de quota renovável. Nos 30 dias, a quota ponderada é de 70,73%.
- Em caso de falha, republica o último dataset publicado no Pages. Se isso também falhar, emite um aviso e o build continua (sai com 0).
- **Validação:** smoke test com fetch simulado cobrindo todos os casos da secção 13, mais oxlint.
